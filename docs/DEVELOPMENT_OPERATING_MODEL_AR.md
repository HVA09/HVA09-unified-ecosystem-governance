# نموذج التشغيل الهندسي الموحد

- **الإصدار:** 1.0
- **التاريخ:** 18 نوفمبر 2026
- **الحالة:** مقترح تنفيذي بانتظار مراجعة ودمج PR.
- **النطاق:** حوكمة دورة التطوير عبر Lumen وAI Chat App وERP وAI Core وUnified Ecosystem.
- **المرجع:** `docs/UNIFIED_ECOSYSTEM_MASTER_PLAN.md` و`docs/TASK_REGISTER.md`.

## 1. الهدف

تحويل التطوير من إضافة مهام متفرقة إلى إغلاق حزم عمل صغيرة قابلة للتحقق، مع حماية استقلال المستودعات والبيانات والنشر. لا يغيّر هذا المستند قرارات المنتج أو يصرّح بإعادة كتابة الأنظمة.

## 2. مصادر الحقيقة

1. هذا المستودع هو مصدر الحقيقة للخطة المشتركة والقرارات والتبعيات العابرة للمشاريع فقط.
2. مستودع كل منتج هو مصدر الحقيقة للكود والاختبارات والإصدارات والتشغيل المحلي لذلك المنتج.
3. لا تنسخ تفاصيل حالة المنتج إلى الخطة المشتركة إلا كملخص مؤرخ مع رابط وSHA.
4. سجل المهام لا يسمح بحالة Done دون دليل قبول قابل للفحص.
5. الأرشيف يحفظ التاريخ ولا يتغلب على الحالة الحية في الفرع الافتراضي.

## 3. دورة حياة المهمة

تمر كل مهمة بالمراحل التالية:

1. **Discover:** فحص main والـPRs والـIssues والـCI والوثائق ذات الصلة.
2. **Specify:** تحديد النطاق والمالك والتبعيات والمخاطر ومعيار القبول.
3. **Implement:** فرع قصير العمر وتغيير محدود داخل المستودع المالك للكود.
4. **Verify:** اختبارات مناسبة للتغيير، وفحص diff والأمن والتوافق.
5. **Review:** مراجعة مستقلة للمنطق والبيانات والصلاحيات والتراجع.
6. **Merge:** الدمج فقط بعد استيفاء حماية الفرع والمراجعات والفحوص المطلوبة.
7. **Post-merge:** التحقق من فحوص main وSmoke/Staging والقبول اليدوي حيث يلزم.
8. **Record:** تحديث سجل المهمة برابط PR وSHA ونتيجة الاختبار والدليل.

## 4. سياسة دفعات التنفيذ

- الحد الافتراضي خمس مهام صغيرة أو متوسطة في دفعة التنفيذ الواحدة عبر البرنامج كله، وليس خمساً لكل مشروع. هذا يحدد عدد المهام التي نعمل عليها في دورة المتابعة، ولا يغيّر وجود 50 حزمة في خارطة البرنامج.
- خارطة البرنامج المعتمدة هي خمس مراحل و50 حزمة (10 لكل مرحلة) وفق `DEC-015` و`docs/UNIFIED_50_TASK_EXECUTION_PLAN.md`. مقترح الـ15 مهمة في `docs/UNIFIED_BATCH_EXECUTION_PLAN.md` تاريخي ومستبدل، وليس دفعة نشطة؛ لا تُعاد تفعيله.
- يمكن بدء مهمة جديدة بحالة Ready إذا تحققت تبعياتها. كما يمكن استئناف مهمة In Progress في دفعة لاحقة بعد مراجعة ما أُنجز وما تبقى؛ لا تُعاد من الصفر ولا تُعامل كعمل جديد. لا تستأنف مهمة Blocked حتى إزالة العائق المسجل.
- يسمح بالتوازي للفحوص والوثائق والمهام المستقلة ذات الملفات/الخدمات غير المتداخلة.
- تنفذ التغييرات المتداخلة أو المعتمدة على بعضها بالتسلسل.
- لا يبدأ أكثر من مسار تغيير عالي المخاطر في قاعدة بيانات أو صلاحيات أو نشر إنتاجي في الوقت نفسه.
- إذا تعذر إنهاء المهمة ضمن الدفعة، تسجل In Progress أو Blocked مع السبب والخطوة التالية، ولا توصف بأنها مكتملة.

## 5. معايير PR

كل PR يجب أن:
- يعالج هدفاً واحداً واضحاً أو مجموعة تغييرات متماسكة.
- يبنى على أحدث main أو يوضح سبب استثناء ذلك.
- يشرح المشكلة والحل والمخاطر وطريقة التراجع.
- يحدد الاختبارات المنفذة ونتائجها.
- لا يضم تنسيقات أو إعادة كتابة غير لازمة.
- لا يحتوي أسراراً أو بيانات إنتاج أو ملفات شخصية.
- يحدّث الوثائق ذات الصلة فقط.

PR المتقادم لا يدمج اعتماداً على نجاح CI تاريخي؛ يعاد تقييمه بعد المزامنة وإعادة الفحوص. الحزم الضخمة تُجزّأ إلى تغييرات مستقلة، ولا تدمج ككتلة واحدة.

## 6. بوابات الجودة والقبول

لا تعد المهمة منجزة إلا بعد استيفاء البوابات المناسبة:
- اختبارات الوحدات والتكامل وواجهات المستخدم والبناء.
- مراجعة الصلاحيات وعزل المستأجرين والبيانات عند الصلة.
- فحص الأسرار والتبعيات والثغرات.
- اختبار التراجع/الاستعادة عند تغيير البيانات أو التخزين.
- اختبار Staging أو قبول يدوي للتكاملات الخارجية والواجهات الحرجة.
- توثيق القياسات قبل/بعد للتغييرات التي تدعي تحسين الأداء.

نجاح CI لا يثبت وحده سلامة النشر أو تجربة الهاتف أو استعادة النسخ الاحتياطية أو تحمل الحمل.

## 7. سياسة الدمج والتغييرات الحساسة

يجوز الدمج الآلي فقط عندما يكون التغيير محدوداً، ومراجعاً، وفحوصه الحالية ناجحة، ولا يحتاج قراراً بشرياً، وتسمح حماية الفرع بذلك. لا يتم تجاوز branch protection.

تتطلب موافقة صريحة وخطة تحقق خاصة:
- migrations أو حذف/تحويل البيانات.
- مفاتيح وأسرار الإنتاج والصلاحيات والهوية.
- تفعيل عزل الشركات أو تغيير حدود المستأجرين.
- نشر إنتاجي أو تغيير مزود/تكلفة مدفوعة.
- عمليات reindex واسعة أو استهلاك موارد مدفوعة.
- تغييرات الاحتفاظ أو الحذف أو مشاركة بيانات المستخدمين.

## 8. الاستقلال والعزل

- مستودع مستقل لكل منتج وخدمة أساسية.
- قواعد بيانات وأسرار وبيئات نشر مستقلة.
- لا يعتمد تشغيل Lumen أو ERP على توافر AI Core.
- التكامل عبر API بإصدارات وعقود موثقة، مع timeouts وretry محدود وcircuit breakers وطوابير عند الحاجة.
- لا تنقل الأكواد بين المستودعات ولا تعِد كتابتها لتغيير اللغة دون دليل أداء أو حاجة صيانة.

## 9. التقارير وإدارة الحالة

في نهاية كل دفعة يسجل:
- المهام المنفذة والمتروكة وأسبابها.
- روابط PRs وcommits وSHA لكل main متحقق منه.
- أسماء الفحوص ونتائجها، مع الفصل بين CI وStaging والقبول اليدوي.
- العوائق والقرارات المطلوبة والمخاطر.
- أولويات الدفعة التالية.

تستخدم الحالات: Proposed، Ready، In Progress، Blocked، Review، Verified، Done، Deferred، Rejected. لا تستخدم Done إذا كان المتبقي اختباراً أو موافقة أو نشر.

## 10. حدود القدرة والموارد

- تبدأ الخطة بأدوات وموارد مجانية حيث أمكن.
- لا تدّعي قدرة ملايين المستخدمين دون سيناريو حمل محدد واختبارات موثقة وقياسات throughput وlatency وerror rate وموارد.
- لا تعتمد قرارات الأداء على لغة البرمجة وحدها؛ تقاس نقاط الاختناق أولاً.
- لا تعتبر فحوص GitHub بديلاً عن تشغيل المنتج محلياً أو على Staging أو على أجهزة حقيقية.

## 11. ترتيب العمل الحالي

1. اعتماد ومصالحة `docs/UNIFIED_50_TASK_EXECUTION_PLAN.md` (50 حزمة فريدة، 10 لكل مرحلة) مع `main` عبر فرع جديد مبني على أحدث `main`؛ يبقى مقترح 15 مهمة في `UNIFIED_BATCH_EXECUTION_PLAN.md` تاريخياً ومستبدلاً.
2. تحديث حالة PRs المتقادمة في AI Chat App وLumen وإعادة تقييمها على أحدث أساس.
3. إغلاق بوابات الاستقرار والقبول في المنتجات الحالية.
4. إكمال فحص ERP على نسخة مستعادة منفصلة قبل أي cutover أو تفعيل multi-tenancy.
5. بعد استقرار الأساس، تنفيذ AI Core وواجهات التكامل تدريجياً.
6. إبقاء المرحلة السادسة (الابتكار والمختبرات والعمليات الذكية) مؤجلة حتى جاهزية المراحل السابقة.
