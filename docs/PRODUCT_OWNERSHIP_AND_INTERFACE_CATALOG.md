# سجل ملكية المنتجات وحدود التكامل

- **الحالة:** سجل ملكية وواجهات أولي — S5-01.
- **المرجع:** المخطط المعماري الرئيسي و`UNIFIED_ENGINEERING_STANDARDS.md` وسجل القرارات.
- **قاعدة الحوكمة:** منظومة واحدة في الرؤية والتنسيق؛ منتجات مستقلة تشغيلياً، والتكامل عبر عقود صريحة.

## 2. قواعد تدفق البيانات

1. يظل كل منتج مالكاً لسجلاته ومفاتيح الوصول إليها وسياسة الاحتفاظ والحذف الخاصة به.
2. لا تنقل بيانات طالب أو مستخدم أو محادثة أو ملف أو شركة إلى منتج آخر إلا لغرض محدد ومصرح به وبأقل قدر لازم.
3. لا يقرأ منتج قاعدة بيانات منتج آخر مباشرة؛ يتم تبادل البيانات عبر API بإصدار وعقد ومالك واضح.
4. يطلب المستهلك البيانات عبر الهوية والصلاحيات التي يعتمدها المنتج المالك؛ لا يُقبل `user_id` أو `company_id` أو `workspace_id` من العميل كإثبات صلاحية وحده.
5. لا تنسخ الذاكرة أو RAG بين المستخدم والمشروع والشركة افتراضياً؛ نطاق التخزين والاسترجاع يجب أن يطابق نطاق التفويض.
6. سجلات المراقبة المشتركة تحمل معرفات تتبع وبيانات تشغيلية دنيا؛ لا تضع نص المحادثة أو محتوى الملف أو الأسرار في سجلات مركزية.

## 3. عقود التكامل المرشحة

| العقد | المالك المقترح | المستهلك المحتمل | شرط الاعتماد |
|---|---|---|---|
| Model/Agent API | AI Core بعد إنشائه | AI Chat App، وربما Lumen أو ERP وفق القرار | إصدار واضح، scopes، timeout/fallback، عدم اعتماد المنتج على توافر النواة |
| Learning API / LMS integration | Lumen | تكامل LMS أو تطبيق مصرح | LTI/AGS وواجهات التعليم الخاصة بـLumen؛ لا يملك AI Core هذه البيانات |
| ERP company context / business API | ERP | واجهة أو موصل مصرح | signed membership context وRLS/tenant isolation؛ لا استخدام مباشر لقاعدة ERP |
| Workspace/Tool contract | المنتج المالك للأداة، مع adapter محتمل | AI Core أو وكلاء المنتجات | tool registry وpermission check وموافقة بشرية للأفعال الحساسة |
| Webhook/Event contract | المنتج المصدر | مستهلك مصرح | توقيع، إصدار، idempotency، retries، DLQ، وحدود بيانات |
| Audit/Telemetry contract | كل منتج يحتفظ بسجله؛ منصة المراقبة تستهلك الحد الأدنى | حوكمة وتشغيل | correlation IDs وسياسة retention ومنع تسريب المحتوى الحساس |

هذه عقود مرشحة للتصميم وليست واجهات جاهزة للتنفيذ. لا يوجد قرار بتوحيد قواعد البيانات أو فرض SSO أو فرض بوابة مركزية واحدة.

## 4. الهوية والتفويض

- تبقى جلسات وهوية Lumen وAI Chat App وERP مستقلة حالياً.
- لا SSO شامل ولا مشاركة session secrets ولا مفاتيح توقيع بين المنتجات في هذه المرحلة.
- أي اتصال خدمة-إلى-خدمة يحتاج هوية مستهلك، audience، scopes، انتهاء صلاحية، تدوير مفاتيح، سجل تدقيق، وخطة إلغاء.
- ERP يتطلب تحقق عضوية شركة وسياقاً موثوقاً؛ المفتاح `TENANT_DATA_SCOPING_ENABLED` يبقى مغلقاً إلى أن تجتاز بوابات الإصدار.
- أدوات الوكلاء يجب أن تعمل بأقل صلاحية، وتطلب موافقة بشرية عند الأفعال المالية أو الإنتاجية أو الحساسة بحسب الخطر.

## 5. الفشل والتعافي

- تعطل AI Core لا يوقف تسجيل الدخول أو عرض المحادثات أو العمليات التعليمية/المالية الأساسية للمنتجات.
- تعطل Unified Ecosystem أو بوابة تكامل لا يوقف منتجاً مستقلاً.
- لا تُنفذ retries غير محدودة ولا عمليات غير idempotent من دون مفتاح منع التكرار.
- كل عقد يحدد timeout وfailure mode وfallback ومؤشرات مراقبة ومالك حادث.
- كل منتج يحتفظ بخطة backup/restore وrollback منفصلة؛ لا تعتمد استعادة منتج على سلامة قاعدة منتج آخر.

### قواعد الحدود بين المنتجات

1. معرفات users وstudents وcompanies محلية لكل منتج؛ لا تفترض تطابق الأرقام ولا تمررها كـprincipal identity.
2. هوية الخدمة المستقبلية تحتاج issuer وaudience وscope وانتهاء صلاحية وإلغاء، مع token/service principal منفصل عن جلسة المستخدم.
3. المنتج المالك وحده يحدد إن كان المستهلك يستطيع قراءة مورد أو تنفيذ فعل؛ أي company/user/resource ID في الطلب ليس authorization proof.
4. لا direct database access بين Lumen وAI Chat App وERP.
5. لا يشارك ERP بيانات الشركة مع AI Core قبل فتح multi-company release gate رسمياً؛ ولا تتجاوز حالة TENANT_DATA_SCOPING_ENABLED=False.
