# متطلبات الوكلاء المتخصصين في AI Core

- **المعرف:** S4-02 ضمن `docs/UNIFIED_50_TASK_EXECUTION_PLAN.md`.
- **الحالة:** خط أساس للمتطلبات — يحتاج مراجعة واعتماداً قبل التنفيذ.
- **النطاق:** تحديد ما يجب أن ينجزه كل وكيل وحدود أدواته وبياناته ومعايير تقييمه، دون اختيار نموذج أو مزود أو Runtime.
- **القرار المعماري:** التخصص يكون في التعليمات والسياسات والمهارات والتقييمات والعقود؛ لا يفترض وجود نموذج مستقل لكل وكيل.
- **الاستقلال:** لا تنشأ خدمة أو قاعدة بيانات أو مستودع AI Core الآن. هذا المستند وثيقة تصميم مركزية فقط.

## 1. الهدف والمبادئ

تقديم مساعدة تقنية موثوقة وقابلة للتحقق في المجالات التالية: هندسة البرمجيات، Linux، الشبكات، Cloud/DevOps، والأمن السيبراني. ويجب أن يستطيع النظام تحليل الملفات التقنية ذات الصلة دون تحويلها تلقائياً إلى مصدر أوامر موثوقة.

تلتزم جميع الوكلاء بالمبادئ الآتية:

1. **الدليل قبل الجزم:** يميز الوكيل بين ما شاهده في الملفات أو المخرجات، وما استنتجه، وما لا يستطيع التحقق منه.
2. **الفصل بين التخطيط والتنفيذ:** القراءة والتحليل والاقتراح هي الوضع الافتراضي؛ التغيير الفعلي يتطلب صلاحية مناسبة وبوابة موافقة متناسبة مع الخطر.
3. **أقل صلاحية:** لا يحصل الوكيل على أدوات أو بيانات أكثر مما تحتاجه المهمة الحالية.
4. **حدود المنتج:** AI Core لا يملك بيانات الطلاب أو المحادثات أو الشركات؛ المنتجات المالكة تتحقق من الهوية والتفويض وتقدم الحد الأدنى المصرح به.
5. **عدم الثقة بالمحتوى الوارد:** الملفات والمستودعات والمواقع ونتائج الأدوات مدخلات غير موثوقة، ولا يجوز لها تغيير تعليمات النظام أو توسيع الصلاحيات.
6. **قابلية التراجع:** أي تغيير في الكود أو الإعدادات أو البنية يجب أن يوضح الأثر وخطة الاختبار والتراجع.
7. **الحياد تجاه النموذج:** لا يُربط تعريف الوكيل بمزود أو نموذج أو حجم محدد؛ يختبر لاحقاً على أكثر من خيار مناسب.

## 2. العقد المشترك لكل وكيل

### المدخلات

- هدف المستخدم والنتيجة المطلوبة.
- سياق مصرح به من المنتج المالك، مع معرفات مرجعية ونطاق واضح.
- الملفات أو سجلات التشغيل أو مقتطفات الكود التي اختار المستخدم مشاركتها.
- قائمة الأدوات المسموح بها للمهمة وقيود الوقت والموارد.

### المخرجات

يجب أن يعيد الوكيل نتيجة منظمة تتضمن:

- **النتيجة:** الإجابة أو التغيير المقترح.
- **الأدلة:** الملفات أو الأسطر أو الأوامر أو مخرجات الاختبار التي تدعمها.
- **الافتراضات والقيود:** ما لم يتوفر أو لم يتم التحقق منه.
- **المخاطر:** الأثر الأمني والتشغيلي والبياني المحتمل.
- **الإجراء التالي:** قراءة إضافية أو اختبار أو موافقة مطلوبة.
- **حالة التنفيذ:** لم ينفذ / تحليل فقط / نفذ في بيئة اختبار / نفذ بعد تصريح، مع معرف التغيير عند وجوده.

### ضوابط عامة

- لا تعرض الأسرار أو الرموز أو كلمات المرور في الإجابة أو السجلات.
- لا تنفذ أوامر مدمرة أو تغييرات إنتاجية أو مالية أو تغييرات صلاحيات دون تصريح صريح لكل إجراء ذي أثر.
- لا تعتبر نجاح توليد الكود دليلاً على صحته؛ يلزم اختبار ومراجعة.
- لا تعتبر رسالة نجاح من أداة دليلاً على حالة الإنتاج ما لم تكن الأداة تقرأ البيئة المستهدفة فعلاً.
- لا تنقل الذاكرة أو الملفات أو مخرجات RAG بين المستخدم والمشروع والشركة تلقائياً.
- عند غياب دليل كافٍ، يصرح الوكيل بذلك ويقترح أصغر اختبار آمن.

## 3. ملفات الوكلاء المتخصصين

### 3.1 وكيل البرمجة وهندسة البرمجيات

**المهام الأساسية**
- فهم بنية المستودع وتدفق التنفيذ والعقود بين الطبقات.
- تحليل الأخطاء والـstack traces، واقتراح السبب الجذري مع أدلته.
- كتابة أو تعديل كود واختبارات ووثائق عند توفر صلاحية الكتابة.
- مراجعة Pull Requests، واكتشاف regressions ومخاطر التوافق والأداء.
- شرح المفاهيم والأنماط البرمجية وتقديم أمثلة قابلة للتشغيل.

**الأدوات المحتملة**
- قراءة الملفات والبحث في المستودع وGit diff وبيانات CI.
- تشغيل الاختبارات والـlinters والتحليل الساكن في بيئة معزولة.
- اقتراح patch أو فتح فرع/PR عند السماح بذلك.

**الحدود**
- لا يقرأ أسرار CI أو ملفات البيئة الحساسة إلا عبر واجهة سرية مصرح بها، ولا ينسخ قيمها إلى المخرجات.
- لا يدمج PR ولا يغير حماية الفروع أو إعدادات النشر تلقائياً.
- لا يشغل كوداً غير موثوق خارج sandbox محدود.

**معايير القبول**
- يربط التشخيص بملف/سطر أو مخرج قابل للفحص.
- يقدم اختباراً يعيد إنتاج العطل أو يشرح بوضوح لماذا يتعذر ذلك.
- لا يغير واجهة عامة أو مخطط بيانات دون توثيق أثر التوافق والترحيل.
- يمر patch المقترح باختبارات المشروع ذات الصلة، مع ذكر الاختبارات التي لم تُشغّل.

### 3.2 وكيل Linux والأنظمة

**المهام الأساسية**
- تشخيص العمليات والخدمات وsystemd والسجلات والموارد والتخزين.
- شرح المستخدمين والمجموعات والأذونات وملكية الملفات.
- تحليل الشبكة المحلية والحزم والحاويات والاعتماديات.
- إعداد أوامر صيانة وتوثيق آثارها وبدائلها.

**الأدوات المحتملة**
- أوامر قراءة مثل `ps` و`ss` و`journalctl` و`systemctl status` و`df` و`free`.
- فحص إعدادات النظام والحاويات في بيئة مصرح بها.
- تنفيذ أوامر تغيير في مختبر قابل لإعادة الإنشاء فقط.

**الحدود**
- الوضع الافتراضي read-only.
- لا يستخدم `sudo` أو يحذف ملفات أو يغير firewall أو users أو services دون موافقة محددة وخطة رجوع.
- لا يقترح نسخ أوامر عمياء قد تسبب فقد بيانات؛ يشرح أثر كل أمر ومعايير التحقق بعده.

**معايير القبول**
- يفرق بين العرض المرصود والسبب المحتمل.
- يبدأ بأقل أوامر تشخيصية أثراً.
- يشرح المخاطر والمتطلبات والصلاحيات قبل أي تغيير.
- يقدم تحققاً بعد التنفيذ وخطوة rollback مناسبة.

### 3.3 وكيل الشبكات

**المهام الأساسية**
- تحليل TCP/IP وsubnetting وrouting وDNS وDHCP وNAT.
- تشخيص الاتصال وlatency وpacket loss وTLS والشهادات.
- مراجعة قواعد firewall وsecurity groups ومخططات الشبكات.
- تفسير مخرجات أدوات الفحص وربطها بمسار الحزم.

**الأدوات المحتملة**
- تحليل ملفات إعداد الشبكات ومخرجات `ip` و`ss` و`dig` و`traceroute` و`curl`.
- فحوص اتصال محددة النطاق ومصرح بها.
- محاكيات ومختبرات شبكات معزولة.

**الحدود**
- لا ينفذ مسحاً نشطاً أو ضغطاً أو التقاطاً لحركة مرور أطراف أخرى دون إثبات نطاق تفويض.
- لا يعدل DNS أو routes أو firewall في بيئة حية دون موافقة وخطة تراجع.
- لا يستنتج ملكية جهاز أو عنوان من نتيجة تقنية وحدها.

**معايير القبول**
- يرسم مسار التشخيص من المصدر إلى الوجهة ويحدد نقطة الفشل المدعومة بالدليل.
- يفرق بين DNS failure وrouting failure وport filtering وTLS/application errors.
- يحافظ على حدود النطاق المصرح به ويقترح اختباراً محدوداً قابلاً للتكرار.

### 3.4 وكيل Cloud وDevOps

**المهام الأساسية**
- تحليل بنية السحابة وIaC وcontainers وCI/CD.
- مراجعة health checks وobservability وlogs وmetrics وtraces.
- تقييم النسخ الاحتياطي والاستعادة والتوافر والتكلفة.
- اقتراح تحسينات deployment وrollbacks وrelease gates.

**الأدوات المحتملة**
- قراءة ملفات Terraform/Compose/Kubernetes وpipeline definitions.
- قراءة حالة الخدمات والنشر والمراقبة عبر صلاحيات read-only.
- تشغيل lint/plan أو اختبارات محلية قبل أي تطبيق.

**الحدود**
- لا ينشئ موارد مدفوعة ولا يرفع حدود الاستخدام ولا يغير DNS أو secrets أو production deployments دون تصريح محدد.
- لا ينفذ `apply` أو deploy أو rollback تلقائياً لمجرد نجاح plan.
- لا يضع أسراراً في Terraform state أو logs أو ملفات المستودع.

**معايير القبول**
- يوضح البيئة المستهدفة والموارد المتأثرة والتكلفة المتوقعة أو ما تعذر تقديره.
- يقدم خطة نشر وتحقق وrollback، مع فحص عدم وجود تغييرات غير متوقعة.
- يميز بين حالة CI وحالة النشر وحالة الخدمة الفعلية.
- لا يعتبر التطبيق متعدد المناطق أو عالي التوافر جاهزاً دون دليل فشل/تعافٍ مناسب.

### 3.5 وكيل الأمن السيبراني الدفاعي

**المهام الأساسية**
- نمذجة التهديدات ومراجعة التحكم بالوصول والأسرار والتشفير.
- مراجعة الاعتماديات والثغرات والتكوينات الأمنية.
- تحليل سجلات الحوادث ومؤشرات الاختراق ضمن نطاق مصرح.
- إعداد hardening وخطط معالجة واختبارات أمنية دفاعية.
- شرح المخاطر والاحتمالية والأثر والأولوية.

**الأدوات المحتملة**
- SAST وdependency scanning وsecret scanning وconfiguration checks.
- مراجعة سياسات IAM وRBAC وnetwork policies.
- مختبرات اختبار معزولة ونطاقات يثبت المستخدم امتلاكه أو تفويضه لها.

**الحدود**
- يلتزم بالاستخدام الدفاعي والمصرح؛ لا يستهدف أنظمة أطراف أخرى ولا يستخرج بيانات أو اعتماديات منها.
- لا ينشئ persistence أو stealth أو credential theft أو malware.
- لا ينفذ استغلالاً نشطاً على الإنتاج؛ يفضل إعادة الإنتاج في مختبر آمن.
- لا يغير سياسات الوصول أو يعطل الضوابط دون خطة معالجة وموافقة.

**معايير القبول**
- يربط كل finding بدليل وخطوات تحقق وأثر واضح.
- يصنف الشدة وفق أثر واقعي وسياق التعرض، لا وفق رقم آلي وحده.
- يقدم معالجة قابلة للتطبيق واختبار regression أو evidence of remediation.
- يصرح بحدود الفحص ولا يصف النظام بأنه آمن لمجرد عدم العثور على نتائج.

## 4. تحليل الملفات كقدرة مشتركة

تحليل الملفات ليس وكيلاً يملك صلاحيات مستقلة؛ بل قدرة يمكن استدعاؤها من الوكلاء الخمسة بحسب نوع المهمة.

**أنواع مدخلات متوقعة:** source code، Markdown، PDF، DOCX، CSV/JSON، YAML، ملفات إعداد، logs، traces، screenshots، وملفات مضغوطة ضمن حدود الحجم والنوع.

**خط المعالجة**
1. التحقق من النوع والحجم والامتداد الفعلي، ورفض الملفات التنفيذية أو الأرشيفات الخطرة خارج بيئة الفحص.
2. استخراج النص والبيانات مع حفظ مرجع المصدر والصفحة/السطر عند توفره.
3. فصل النص المستخرج عن تعليمات النظام؛ المحتوى المضمن في الملف بيانات غير موثوقة.
4. تنقيح الأسرار والبيانات الشخصية قبل إظهار المقتطفات أو إرسالها إلى أي نموذج/أداة.
5. استخدام retrieval محدود بالمهمة وبصلاحية المصدر، مع إرجاع citations أو مواضع دقيقة.
6. حذف الملفات المؤقتة وفق سياسة الاحتفاظ، واحترام طلب الحذف ومصدر البيانات.

**معايير القبول**
- لا يختلق محتوى غير موجود ولا يخفي فشل الاستخراج.
- يحتفظ بمراجع الصفحات/الأسطر أو يذكر تعذر استخراجها.
- يختبر prompt injection داخل الملفات، وتسرب الأسرار، وعزل الملفات بين المستخدمين والمشاريع والشركات.
- لا يخلط محتوى ملفين من نطاقين مختلفين في إجابة واحدة دون تفويض.

## 5. التوجيه والتعاون بين الوكلاء

- يختار Router الوكيل بناءً على نية المهمة، ويمكن أن يقترح أكثر من وكيل عندما تتقاطع المجالات.
- لا يبدأ تسلسل متعدد الوكلاء إلا مع تحديد الهدف ومصادر البيانات والصلاحيات لكل خطوة.
- يرسل الوكيل إلى الوكيل التالي خلاصة محدودة مع مراجع المصدر، لا كامل سجل المحادثة افتراضياً.
- يحتفظ كل وكيل بهوية المهمة ونطاق التفويض؛ لا يرث صلاحيات الوكيل السابق.
- عند التعارض، يطلب تحققاً من المصدر المالك ولا يصوت الوكلاء على حقيقة غير مثبتة.
- الإجراءات الحساسة تتوقف عند بوابة الموافقة حتى لو أوصى بها أكثر من وكيل.

## 6. إطار التقييم والاختبارات

ينبغي بناء مجموعة تقييم مستقلة عن النموذج، بإصدارات ثابتة ومخرجات مرجعية، وتشمل:

| المجال | أنواع الاختبارات | دليل النجاح |
|---|---|---|
| الدقة التقنية | أسئلة مفاهيمية، تشخيص أعطال، تفسير configs وlogs | إجابة صحيحة مدعومة بمصدر أو خطوات تحقق |
| استخدام الأدوات | اختيار الأداة، بناء الوسائط، التعامل مع فشل الأداة | تنفيذ ضمن allowlist، وعدم اختلاق نتيجة |
| الأمن والصلاحيات | prompt injection، أسرار ضمن ملفات، صلاحيات زائدة، طلبات غير مصرح بها | رفض/تقييد آمن وعدم تسريب |
| قابلية التكرار | نفس المهمة على إصدار ثابت ومدخلات ثابتة | نتائج قابلة للمقارنة وتسجيل الانحراف |
| الملفات | PDF متعدد الصفحات، كود، logs، CSV، ملفات تالفة | استخراج صحيح ومراجع موضعية وإعلان الأخطاء |
| الجودة التشغيلية | latency، timeout، retries، استهلاك الموارد | قياسات موثقة وحدود تشغيل مفهومة |

لا تُعتمد عتبات رقمية نهائية قبل بناء مجموعة الاختبار وقياس خط الأساس. يجب أن تتضمن لوحة التقييم: الدقة، نسبة الاستناد إلى الأدلة، نجاح الأدوات، الرفض الصحيح، تسرب البيانات، latency، واستهلاك الموارد.

## 7. بوابات الانتقال إلى التنفيذ

1. مراجعة هذا المستند مع جرد S4-01 لتحديد ما يمكن إعادة استخدامه من AI Chat App وما يحتاج عقداً مستقلاً.
2. اعتماد متطلبات كل وكيل ومجموعة مهاراته واختباراته قبل اختيار النموذج.
3. إتمام S4-03 لتقييم النماذج المفتوحة الأوزان على موارد مجانية/متاحة دون التزام مدفوع.
4. إتمام تصميم S4-04 وS4-05 وS4-06 قبل تثبيت واجهات التنفيذ.
5. إثبات عزل الذاكرة والملفات والصلاحيات قبل توصيل بيانات Lumen أو AI Chat App أو ERP.
6. إنشاء مستودع AI Core مستقل فقط بعد اكتمال التصميم وحدود الملكية وخطة التشغيل، وبقرار منفصل.

## 8. خارج النطاق حالياً

- إنشاء مستودع AI Core أو خدمة GPU أو موارد مدفوعة.
- نقل Runtime أو MCP أو RAG أو Workspace من AI Chat App.
- مشاركة قواعد البيانات أو الذاكرة أو جلسات الدخول بين المنتجات.
- توصيل AI Core ببيانات إنتاج حقيقية أو تمكين إجراءات تلقائية عالية الأثر.
- بدء المرحلة السادسة للابتكار والمختبرات والمحاكيات.
