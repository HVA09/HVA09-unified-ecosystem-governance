# سجل التعارضات والمصالحة

- **تاريخ المراجعة:** 16 نوفمبر 2026
- **الحالة:** مراجعة وثائق ومراجع GitHub فقط؛ لا تغييرات في كود المشاريع أو قواعد البيانات أو بيئات الإنتاج.
- **مبدأ الحسم:** لا ندمج وثيقتين متعارضتين بالنص أو التخمين. نسجل مصدر كل ادعاء، ونميز الحالة الفعلية عن التاريخ والاقتراح.

## 1. سياسة أولوية المصدر

1. رأس الفرع الفعلي في GitHub يحدد حالة الكود، لا SHA مكتوب داخل ملف قديم.
2. بيانات PR الحية تحدد Draft/Open/Merged والـBase/Head؛ وصف PR لا يثبت نجاح CI الحالي وحده.
3. CI لا يُعتمد إلا إذا كان على Head SHA نفسه الذي نراجعه.
4. نتائج الاختبار الآلي لا تثبت نجاح التكامل الخارجي أو قبول المستخدم.
5. ملفات الاستمرارية والتقارير هي سجلات مؤرخة؛ إذا تعارضت مع GitHub الحالي، تُعلّم بأنها تاريخية إلى أن تُحدّث في مستودعها الأصلي.
6. المستودع المركزي ينسق السياسات المشتركة فقط. لا يفرض بنية موحدة على قواعد البيانات أو يلغي مواثيق الجودة الخاصة بكل منتج.

## 4. ERP

- `README.md` يحتوي ملخصاً عند Stage24 بينما main لديه ملفات Stage25B وStage25C.

**المصالحة:** SHA من GitHub main هو مرجع الكود الحالي. يجب تحديث continuity/governance/README داخل ERP في عمل توثيقي مستقل، مع الحفاظ على سجل المراحل القديمة. لا يجرى هذا التحديث من المستودع المركزي.

### 4.2 لا تُخلط مواصفات PostgreSQL مع ترحيل منفذ

- SQLite v8 هي قاعدة التطبيق النشطة الموثقة.
- `TENANT_DATA_SCOPING_ENABLED=False`؛ تشغيل العمليات متعددة الشركات محظور/Fail-closed.
- Stage25B قرار ومواصفة لمصدر حقيقة الهوية وعقد migration.
- Stage25C دليل محلي لفحص نسخة SQLite في وضع القراءة فقط.
- تقارير CI/Preflight الحالية تستند إلى بيانات اصطناعية؛ لم يتوفر تقرير على نسخة قاعدة فعلية مستعادة من المستخدم.
- لا يوجد ما يثبت PostgreSQL cutover أو dual-write أو تطبيق RLS على جميع جداول الأعمال.

**المصالحة:** لا تفعّل multi-company، ولا PostgreSQL أو RLS في التطبيق، ولا تنفذ ETL قبل Preflight فعلي ومراجعة التقرير واختبارات reconciliation وrollback على قواعد مؤقتة.

### 4.3 أولوية وثائق ERP

استخدم المعمارية وقرارات ADR والـbacklog وStage25B/25C لفهم الاتجاه الحالي. اعتبر ملفات Stage 1–24 سجلاً تاريخياً لمراحل منفذة/مقترحة حسب أدلة كل مرحلة، لا قائمة عمل حديثة تلقائياً.

## 5. تعارضات مشتركة بين المنتجات

### 5.1 مواثيق الجودة — توحيد مشترك مع ملاحق محلية

توجد نسخ من Engineering Quality Covenant داخل المشاريع الثلاثة. تمت المقارنة النصية في 16 نوفمبر 2026، ووجدنا أن:
- الجزء المشترك قبل `## ملحق خاص بالمشروع` (الغاية والأقسام 1–12) متطابق حرفياً في Lumen وAI Chat App وERP.
- القسمين 13 و14 (الممارسات الهندسية المرجعية والمصادر) متطابقان حرفياً أيضاً.
- الاختلاف المقصود هو الملحق المحلي لكل مشروع، ويجب عدم إلغائه لأنه يحمل قيود التقنية والبيانات والاختبارات الخاصة بالمنتج.

**المصالحة:** جُمعت الأجزاء المشتركة في `docs/UNIFIED_ENGINEERING_STANDARDS.md`. تبقى مواثيق المشاريع الأصلية وملاحقها نافذة؛ لا يستبدل الملف المركزي نسخها. أي تغيير مشترك لاحق يُزامن عبر PR توثيقي منفصل في المستودعات المتأثرة.
 
### 5.2 الهوية والصلاحيات

لا يجوز تحويل الرغبة في تكامل واحد إلى حساب مشترك أو صلاحيات مشتركة قبل توثيق user lifecycle وtenant scope وconsent وrevocation وaudit وfailure mode. لا مشاركة session أو JWT signing keys بين المنتجات كحل سريع.

### 5.3 التسمية لا تعني فصل الخدمة

لا ننشئ AI Core بمجرد نقل أسماء الوكلاء. يلزم إثبات قابلية إعادة الاستخدام، وحدود أمنية، ومقاييس جودة، وتكلفة التشغيل، وخطة fallback لكل منتج.

### 5.4 التوثيق لا يثبت التشغيل

لا تُستنتج حالة نشر أو backup أو branch protection أو بيانات إنتاج من ملف قديم فقط. يجب تدوين المصدر والتاريخ وطريقة التحقق.

## 5.5 ميثاق الجودة المشترك والملاحق المحلية

- الجزء المشترك من مواثيق `ENGINEERING_QUALITY_COVENANT_AR.md` في المنتجات الثلاثة متطابق: القسم المشترك قبل ملحق المشروع (الأقسام التمهيدية و1–12) والقسمان 13 و14 بعد الملاحق.
