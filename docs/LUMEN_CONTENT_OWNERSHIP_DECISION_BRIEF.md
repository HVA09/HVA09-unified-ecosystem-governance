# مذكرة قرار: ملكية الأسئلة والدروس في Lumen

- **المعرّف:** LUM-010 / قرار منتج مطلوب
- **التاريخ:** 17 نوفمبر 2026
- **الحالة:** Open — أدلة التدقيق موثقة؛ لم يعتمد مالك المنتج سياسة الملكية بعد.
- **مصدر الكود:** `HVA09/lumen-learning-platform`، `main` عند `fe3a87591a6a6c5f909b0dba162cdd8b4ba47ce8`.
- **حدود المذكرة:** تحليل وقرار مقترح فقط. لا تغيّر هذه المذكرة سلوك التطبيق أو قاعدة البيانات أو الصلاحيات.

## 1. الملخص التنفيذي

مسارات `/content` الحالية تعامل بنك الأسئلة والدروس على أنهما محتوى عام على مستوى الموضوع: أي حساب يحمل دور teacher أو admin يستطيع قراءة عناصر الموضوع وتعديلها وحذفها. هذا يتفق جزئياً مع بنية المنهج المشتركة، لكنه يمنح كل معلم سلطة كتابة وحذف على محتوى أنشأه معلم آخر.

المنصة تملك بالفعل نموذجاً مختلفاً وأكثر تحديداً في الفصول والواجبات: الفصل للمعلم المالك، والواجب يديره منشئه أو admin. لذلك لا يجوز افتراض أن جميع الموارد التعليمية تشترك في قاعدة ملكية واحدة.

**التوصية المقترحة:** اعتماد نموذج «قراءة مشتركة، وكتابة للمنشئ أو المدير» كخط أساس انتقالي، مع حماية المحتوى المزروع من النظام ليكون تعديله للمدير فقط. تبقى الدروس والأسئلة المنشورة قابلة للعرض في المنهج المشترك كما هي حالياً إلى أن يعتمد المالك سياسة مختلفة للرؤية أو النشر. هذه توصية وليست قراراً معتمداً.

## 2. أدلة المصدر على Lumen main

### 2.1 مسارات الأسئلة والدروس

في `backend/app/routers/content.py`:

- `GET /content/topics/{topic_id}/questions` و`GET /content/topics/{topic_id}/lessons` يسترجعان جميع عناصر الموضوع.
- الإنشاء والتعديل والحذف تستخدم `Depends(require_teacher)`، أي teacher أو admin.
- التعديل والحذف يجلبان المورد بواسطة المعرف فقط؛ لا يقارنان المستخدم الحالي بمنشئ المورد أو بمالك الموضوع.
- إنشاء السؤال يملأ `Question.created_by_user_id = teacher.id`، لكن مساري التعديل والحذف لا يستخدمان هذا الحقل.
- إنشاء الدرس لا يسجل هوية المنشئ.

### 2.2 نماذج البيانات والمنهج المزروع

- `Question` يملك `created_by_user_id` اختيارياً، و`key` ثابتاً للأسئلة المزروعة.
- `Lesson` لا يملك حقل منشئ أو مالك.
- `Topic` و`Subject` لا يحملان مالكاً من نوع user أو teacher؛ المحتوى منظم على مستوى المنهج/الموضوع.
- `backend/app/content/seeder.py` يضيف الدروس والأسئلة الجاهزة باستخدام `slug` و`key`، ولا يكتب creator للصفوف المزروعة ولا يستبدل سجلاً موجوداً.
- `backend/app/content/updater.py` لا يحدث حقلاً إلا إذا ظل مطابقاً حرفياً للنص القديم المزروع؛ واختبارات `test_content_refresh.py` تثبت عدم الكتابة فوق تعديلات المعلم.
- واجهة الطالب في `backend/app/routers/curriculum.py` تعرض كل الدروس المنشورة للموضوع، ولا تربطها بفصل أو منشئ.

هذه الأدلة تشير إلى نية محتوى منهجي مشترك وقابل لتحرير المعلم، لكنها لا توثق سياسة تفويض معتمدة للتعديل المتبادل.

### 2.3 نماذج ملكية مطبقة في أجزاء أخرى

- `ClassSection.teacher_user_id`: إدارة الفصل محصورة بالمعلم المالك أو admin.
- `Assignment.created_by_user_id`: `_can_manage()` يسمح للمنشئ أو admin بإدارة الواجب، وتوجد اختبارات مخصصة لمنع معلم آخر من إدارة تسليماته.
- هذا يثبت أن النظام يستخدم ملكية المورد عند الحاجة، لكنه لا يحسم أن المحتوى المنهجي يجب أن يتبع النموذج نفسه.

### 2.4 تغطية الاختبارات الحالية

- `backend/tests/test_content.py` يختبر إنشاء/تعديل/حذف السؤال بواسطة المعلم نفسه، ودورة حياة الدرس بواسطة معلم واحد، وإنشاء سؤال بواسطة admin.
- لا يظهر اختبار ينشئ المعلم A محتوى ثم يحاول المعلم B تعديله أو حذفه.
- اختبارات الواجهة `ContentManager.test.jsx` تتحقق من إرسال الطلبات وتحديث القوائم، لكنها لا تختبر اختلاف صلاحيات معلمين.
- لا يوجد اختبار cross-teacher يثبت هل المحتوى المشترك مقصود أم أن غياب فحص الملكية فجوة.

## 3. خيارات السياسة

| الخيار | السلوك | الأثر والمخاطر |
|---|---|---|
| A — تحرير مشترك كامل | كل teacher يستطيع قراءة وتعديل وحذف كل محتوى الموضوع؛ admin كذلك | يحافظ على السلوك الحالي؛ لكنه يسمح بتغييرات أو حذف غير مقصود لمحتوى معلم آخر. يتطلب توثيقاً واختبارات واضحة، وربما سجل نسخ/استعادة. |
| B — قراءة مشتركة وكتابة للمنشئ/admin | كل المعلمين يقرؤون المحتوى؛ المنشئ أو admin فقط يعدّل ويحذف محتوى المعلم؛ المحتوى المزروع/غير المنسوب يديره admin | يقلل مخاطر الكتابة المتبادلة ويحافظ على ظهور المحتوى المنشور للطلاب كما هو. يحتاج إضافة منشئ للدروس وحماية الأسئلة الموجودة. |
| C — نطاقات فصل/مدرسة | كل عنصر يرتبط بصف أو مدرسة/جهة؛ الوصول والتعديل حسب العضوية والنطاق | يمنح عزلاً أدق، لكنه يتطلب نموذج نطاقات جديداً، تغييرات API وواجهات وبيانات واختبارات انتقال، ولا ينبغي إدخاله ضمن إصلاح صغير لـLUM-010. |

## 4. التوصية المقترحة — الخيار B

1. **القراءة:** يبقى بنك الأسئلة والمحتوى المنشور قابلاً للقراءة للمعلمين المخولين، وتبقى رؤية الطلاب للدروس المنشورة على سلوكها الحالي حتى يقرر المالك غير ذلك.
2. **محتوى المعلم:** المنشئ أو admin فقط يمكنه التعديل والحذف. لا يُسمح لمعلم آخر بتغيير ملكية عنصر أو تمرير `created_by_user_id` من العميل.
3. **المحتوى المزروع/القديم غير المنسوب:** يعامل على أنه system-owned ويكون تعديله أو حذفه للـadmin فقط، ما لم توجد أدلة موثوقة تسمح بإسناده إلى معلم معين.
4. **الأسئلة:** إعادة استخدام `created_by_user_id` الموجود، مع التمييز بين الأسئلة المزروعة ذات `key` ثابت وبين الأسئلة التي أنشأها المعلم. لا يثبت وجود `key` وحده أن العنصر غير قابل للتعديل؛ يجب أن تحدد السياسة صلاحية admin.
5. **الدروس:** إضافة حقل منشئ اختياري عبر migration مستقلة بعد اعتماد القرار؛ تبقى العناصر القديمة غير المنسوبة admin-managed. لا تنفذ backfill تخمينياً.
6. **النشر:** لا نخلط ملكية التعديل مع رؤية الطالب. أي تقييد محتوى بمعلم أو فصل يحتاج قراراً مستقلاً وعقداً واضحاً في `/curriculum/topics/{id}/lessons`.

## 5. اختبارات القبول المطلوبة قبل إغلاق LUM-010

- teacher A ينشئ سؤالاً ودرساً؛ ويثبت أن creator يساوي حسابه من جهة الخادم.
- teacher B يستطيع القراءة وفق السياسة المعتمدة، لكنه لا يستطيع تعديل أو حذف محتوى A (403 أو 404 وفق سياسة إخفاء الموارد).
- teacher A يستطيع تعديل وحذف محتواه.
- admin يستطيع إدارة محتوى جميع المعلمين والمحتوى المزروع.
- teacher لا يستطيع تعديل/حذف سؤال أو درس مزروع أو قديم بلا creator.
- الطلبات التي تحتوي حقول creator/owner من العميل لا تغير مالك المورد.
- اختبارات تزامن/سباق عند تعديل أو حذف عنصر واحد من معلمين مختلفين.
- الطلاب لا يحصلون على `correct_answer` أو بيانات إدارة المحتوى عبر مسارات المنهج.
- اختبارات API وBrowser E2E تبين أن واجهة Content Manager تتعامل مع رفض الصلاحية بوضوح.
- migration/upgrade/downgrade واختبار استعادة على قاعدة مؤقتة، دون المساس بقاعدة إنتاج.

## 6. ما لا ينبغي فعله الآن

- لا تضف فحص owner أو migration قبل اعتماد السياسة؛ فقد يؤدي ذلك إلى حجب معلمين عن محتوى كانوا يديرونه عمداً.
- لا تجعل كل محتوى موضوع مرتبطاً بفصل دون تصميم رؤية الطلاب/التقدم/الاختبارات.
- لا تعِد إسناد سجلات قديمة إلى معلمين بالتخمين.
- لا تعتبر غياب الاختبارات دليلاً على وجود استغلال أمني مؤكد؛ الحالة الحالية فجوة سياسة/اختبار تحتاج قراراً واختبارات سلبية.
- لا تغلق LUM-010 أو S1-02 لمجرد اكتمال هذه المذكرة.

## 7. قرار مالك المنتج المطلوب

اختر سياسة واحدة قبل التغيير:

- **A:** تحرير مشترك كامل بين جميع المعلمين.
- **B:** قراءة مشتركة، وتعديل/حذف للمنشئ أو admin، والمحتوى المزروع/غير المنسوب للـadmin فقط. *(الموصى به كخط أساس آمن).*
- **C:** عزل المحتوى حسب الفصل/المدرسة، مع مشروع نطاقات مستقل.

حتى اعتماد القرار، تظل LUM-010 في حالة In Progress، ولا يتغير سلوك Lumen.
